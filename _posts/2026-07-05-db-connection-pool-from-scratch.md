## 한 줄 정의 (Feynman)
> **커넥션 풀은 "매번 새로 열면 비싼 DB 연결"을 미리 몇 개 열어두고 재사용하는 캐시다.**

연결하는 것 자체가 정작 쿼리보다 비싸다.
네트워크 왕복에, 인증에, DB 서버가 프로세스까지 하나 새로 띄워야 하기 때문이다.
그래서 한 번 연 선을 안 끊고, 빌려줬다 반납받으며 계속 우려먹는다. 그게 풀이다.

그런데 "그럼 풀을 크게 잡으면 되지 않나?"가 안 통한다.
이게 이 글의 핵심이다.
풀은 성능 장치일 뿐 정합성과는 아무 상관이 없고, 크기를 키우면 오히려 느려지고, 백엔드를 늘리면 DB가 죽는다.
왜 그런지를 바닥부터 파봤다.

## 1. 핵심 내용 / 구조

### 왜 "서버"부터 헷갈렸을까?

솔직히 나는 여기서부터 막혔다.
"백엔드도 서버고 DB도 서버인데 뭐가 다르지?" 하는 지점이다.

원인은 "서버"라는 단어가 두 가지 뜻으로 쓰이기 때문이었다.

- **서버(머신)**: CPU·RAM·디스크 달린 컴퓨터 한 대.
- **서버(프로그램)**: 요청을 기다렸다 응답해주는 소프트웨어. PostgreSQL, Gunicorn 같은 것.
- **프로세스**: 그 프로그램이 실제로 CPU 위에서 돌아가는 실행 단위. 자기만의 메모리 공간을 가진다.

```text
[머신 1대]  CPU 8코어 / RAM 32GB
  └ OS (Linux)
      └ PostgreSQL "서버(프로그램)" 하나 실행
           ├ postmaster 프로세스     ← 부모 (1개)
           ├ backend 프로세스         ← 커넥션 A 전담
           ├ backend 프로세스         ← 커넥션 B 전담
           └ ... 커넥션마다 1개씩 fork
```

핵심은 **프로그램 하나가 프로세스를 여러 개 거느린다**는 것이다.
Gunicorn(워커 프로세스 N개)도, PostgreSQL(커넥션당 backend 프로세스)도 똑같은 구조다.

### 백엔드는 DB랑 무슨 언어로 대화할까?

처음엔 "HTTP/REST로 DB랑 통신하겠지"라고 막연히 생각했다.
아니었다.

```text
[브라우저] ──HTTP/REST──▶ [백엔드 서버] ──DB wire protocol──▶ [DB 서버]
                          (Flask, 로직)   (HTTP 아님!)         (PostgreSQL, 데이터)
```

- 백엔드는 브라우저한테는 "서버"지만, DB한테는 **"클라이언트"**다. 요청하고 응답받으니까.
- 백엔드↔DB는 HTTP/REST가 아니라 **각 DB 고유의 wire protocol**(TCP 위 바이너리)로 대화한다.
- 그래서 제품마다 **드라이버**가 다르다. `psycopg2`는 PostgreSQL용, `mysqlclient`는 MySQL용이다.

편지에 비유하면 3층이다.

```text
[ SQL "SELECT * FROM orders" ]   ← 편지 "내용"
      │ 감싸서
[ DB wire protocol 메시지 ]       ← 편지 "봉투" (제품마다 규격이 달라서 드라이버가 다르다)
      │ 실려서
[ TCP payload ]                   ← "우편 트럭" (헤더가 아니라 짐칸에 실린다)
```

### 커넥션은 왜 비쌀까?

커넥션 하나를 새로 열 때 실제로 이런 일들이 벌어진다.

```text
1. TCP 3-way handshake     ← 네트워크 왕복
2. TLS handshake           ← (암호화 시) 네트워크 왕복 더
3. 인증 (SCRAM 해시 교환)    ← 네트워크 왕복 + CPU 연산
4. 서버가 backend 프로세스 fork ← DB 머신의 CPU·메모리 일 (PostgreSQL은 커넥션=프로세스, MySQL은 스레드)
```

웹 요청은 보통 "쿼리 한두 개(1ms) 날리고 끝"이다.
그런데 매 요청마다 저 준비(~10ms)를 다 하면, 일보다 준비가 더 비싸진다.
그래서 한 번 연 커넥션을 재사용하자는 게 바로 **풀**이다.

## 2. 무엇을 배웠나

- **풀의 이득은 "재사용"이다.** 1~4단계를 매번 안 해도 된다. (직접 재보니 재사용이 ~19배 빨랐다 — 5번 참고)
- **커넥션 1개는 전화선 한 가닥이다.** 한 번에 쿼리 하나만 돌아간다. 동시에 두 개는 못 태운다.
- **풀 10개에 요청 15개가 오면**, 10개는 즉시 실행되고 나머지 5개는 큐에서 기다린다. 이 대기 시간이 `connection acquisition time`이고, 너무 길어지면 pool timeout 에러가 난다.
- **자원은 OS가 나눠준다.** CPU는 시간을 쪼개고(컨텍스트 스위칭), RAM은 가상메모리로 격리한다. 단 락·캐시 같은 협업 데이터는 공유 메모리 한 곳에서 다 같이 본다.
- **컨텍스트 스위칭은 공짜가 아니다.** 레지스터·프로그램 카운터를 저장/복원하고 캐시/TLB가 무효화된다. 그래서 코어보다 프로세스가 많아지면 이 낭비가 커진다. **이게 "풀 키우면 오히려 느려진다"의 정체였다.**

## 3. 내가 오해하고 있던 것
> 학습 효과가 제일 큰 부분. 이번에 실제로 깨진 오해들을 솔직하게 적었다.

| 이렇게 오해했다 | 직접 파보니 이랬다 |
|---|---|
| "서버 = 프로세스" | 서버(프로그램)와 프로세스는 다르다. 프로그램 하나가 프로세스 여러 개를 거느린다 |
| "HTTP/REST로 DB랑 통신한다" | 백엔드↔DB는 DB 고유 wire protocol이다. HTTP가 아니다. 그래서 제품마다 드라이버가 다르다 |
| "SQL이 TCP 헤더에 실려간다" | SQL은 헤더가 아니라 payload(짐칸)에 실린다. 게다가 SQL↔TCP 사이에 DB 프로토콜(봉투) 층이 하나 더 있다 |
| "DB가 커넥션 풀을 유지한다" | 풀은 보통 앱(클라이언트) 쪽 물건이다. DB는 그냥 "커넥션 N개 꽂혀있네" 하고 볼 뿐이다 |
| "열어둔 커넥션 = 자원 낭비" | 절반만 맞았다. 매번 여는 것보단 훨씬 싸다. 단 오버사이징된 풀은 진짜 낭비다 (그 직감은 그때 맞다) |
| "풀 키우면 처리량 올라간다" | 아니었다. DB 동시 처리량은 코어/디스크에 묶여서, 초과 커넥션은 스위칭·락 경합만 유발한다 |
| "커넥션 1개가 서버 하나를 통째로 문다" | 아니다. DB 머신 한 대 안의 프로세스 1개일 뿐이다 (RAM 몇 MB + 슬롯 하나) |
| "정합성은 풀이 보장한다" | 아니다. 정합성은 DB의 트랜잭션·락·MVCC가 보장한다. 풀은 성능 담당이라 완전히 별개 레이어다 |

왜 헷갈렸을까?
"서버"라는 단어의 이중 의미(머신 vs 프로그램) 때문이었다.
그리고 브라우저↔백엔드 통신(HTTP)을 백엔드↔DB에도 그대로 갖다 붙인 탓도 컸다.
프로세스·자원 구조를 안 들여다보고 풀을 "그냥 크게 잡으면 되는 것"으로 착각했던 것이다.

## 4. 언제 쓰고, 언제 쓰지 않는가 (Trade-offs)

### 풀 크기

| 상황 | 판단 | 이유 |
|---|---|---|
| 매 요청 새 커넥션 | ❌ | 준비 비용을 매번 지불한다 |
| 거대한 풀(200개) | ❌ | idle 커넥션도 메모리·슬롯을 점유하고, 스위칭/경합으로 오히려 느려진다 |
| 적정 풀 `(코어×2)+디스크` | ✅ | HikariCP "About Pool Sizing"의 경험식 |

### 격리 수준 (Isolation Level)

| 수준 | 특징 |
|---|---|
| Read Committed | PostgreSQL 기본. 대부분 여기 두고 필요한 곳만 락을 건다 |
| Repeatable Read | 트랜잭션 내내 같은 스냅샷을 본다 |
| Serializable | 가장 안전하지만 abort/재시도가 늘어 느리다 → 그래서 기본으론 안 쓴다 |

### 확장 3대장

| 레버 | 무엇을 하나 | 한계 |
|---|---|---|
| **Scale Up** (CPU/RAM 증설) | 한 대의 천장을 올린다 | I/O·락 병목엔 무용지물, 비용·최대 크기 한계 |
| **Scale Out** (읽기 복제본·샤딩) | 대수를 늘린다 | 복제 지연, 샤딩은 복잡도가 확 오른다 |
| **Decouple** (PgBouncer) | 앱 커넥션 수와 DB 커넥션 수를 분리한다 | capacity 자체를 늘리진 않는다 |

실무 순서는 보통 이렇다.
① 병목 진단(공짜) → ② 쿼리·인덱스 튜닝(공짜) → ③ decouple/PgBouncer(싸다) → ④ scale up(돈) → ⑤ scale out(복잡).
싸고 안전한 것부터 하고, 돈·복잡도가 드는 건 맨 마지막에 손댄다.

## 5. 직접 실험

말로만 이해하면 금방 잊는다.
로컬에 임시 PostgreSQL 16 (`max_connections=25`)을 띄워서 직접 재봤다.

### 실험 1 — lost update, 눈으로 보기

동시 워커 20개가 카운터를 `+1` 한다. 기대값은 당연히 20이다.

```bash
# ① 비원자적: 읽고(커넥션 A) → 셸에서 +1 → 쓰기(커넥션 B). 읽기~쓰기 사이 '틈'이 생긴다
cur=$(psql -tAqc "SELECT val FROM counter WHERE id=1;")
psql -tAqc "UPDATE counter SET val=$((cur+1)) WHERE id=1;"

# ② FOR UPDATE: 한 트랜잭션에서 행을 잠그고 갱신
psql -c "BEGIN; SELECT val FROM counter WHERE id=1 FOR UPDATE; UPDATE counter SET val=val+1 WHERE id=1; COMMIT;"

# ③ 원자적: DB가 읽기+계산+쓰기를 한 방에
psql -c "UPDATE counter SET val=val+1 WHERE id=1;"
```

실측 결과다.

| 방식 | 기대 | 실제 | 증발 |
|---|---|---|---|
| ① 비원자적 (read→계산→write) | 20 | **3** | **17** |
| ② SELECT … FOR UPDATE | 20 | 20 | 0 |
| ③ 원자적 UPDATE val=val+1 | 20 | 20 | 0 |

20 중에 17개가 증발한 걸 보고 좀 놀랐다.
①은 "읽은 값(예: 5)을 앱이 들고 있는 틈에 남이 먼저 써버려서" 낡은 값으로 덮어쓴 것이다. 이게 lost update다.
②는 행을 잠가 줄을 세우고, ③은 DB가 틈 없이 한 덩어리로 처리해서 막아준다.

### 실험 2 — too many clients

`max_connections=25`인데 커넥션 35개를 동시에 열어봤다.

```bash
for i in $(seq 1 35); do ( psql -tAqc "SELECT pg_sleep(3);" ) & done; wait
```

결과는 시도 35 → **성공 25 (= max_connections 상한) / 거부 10**.
거부될 때 나온 메시지는 `FATAL: sorry, too many clients already`였다.

EKS에서 `Pod 3 × 워커 4 × 풀 10 = 120`이 `max_connections 100`을 넘으면 정확히 이 에러가 난다.
DB는 멀쩡한데 앱이 죽는, 그 전형적인 상황이다.

### 실험 3 — 재사용이 정말 빠를까? (풀이 존재하는 이유)

`SELECT 1`을 50번 실행하는데, (A) 매번 새 커넥션 vs (B) 커넥션 1개 재사용으로 비교했다.

| 방식 | 시간 |
|---|---|
| A) 매번 새 커넥션 | **765 ms** |
| B) 커넥션 1개 재사용 | **41 ms** |

재사용이 약 19배 빨랐다.
이 차이가 곧 커넥션 준비비용(핸드셰이크+인증+fork)인 셈이다.
다만 A는 `psql` 프로세스 기동 비용까지 같이 포함돼서 순수 커넥션 비용을 좀 과대평가한다. 그래도 "재사용이 압도적으로 싸다"는 방향은 확실했다.

## 6. 다른 개념과의 연결

### 락은 대체 어떻게 "강제"될까?

처음엔 락이 그냥 "약속" 같은 건 줄 알았다.
아니었다. 락은 행을 수정하는 유일한 코드 경로에 박힌, 우회 불가능한 검문소다.
그 사슬을 따라 내려가면 결국 하드웨어까지 닿는다.

```text
앱: BEGIN + FOR UPDATE / 원자적 UPDATE     ← 락을 "요청"
 └ DB 실행 경로: 행 수정하려면 락 체크 필수  ← 우회 불가 (강제)
    └ 행(tuple) 헤더 xmax에 XID 도장         ← 락 "기록" (Postgres는 백만 행 잠가도 메모리가 안 터진다)
       └ 공유 메모리 lock table + XID 락 대기 ← 프로세스 간 "조율" (그래서 공유 메모리여야 한다)
          └ spinlock / LWLock 으로 보호
             └ CPU 원자 명령 CAS/test-and-set ← 최종 보증 = 하드웨어 원자성
```

- **MVCC**: 읽기는 마지막 커밋 버전(스냅샷)을 봐서 안 막힌다. 그래서 "읽기가 쓰기를, 쓰기가 읽기를 안 막는" 것이다.
- **데드락**: A가 행1 잡고 행2 원하고, B가 행2 잡고 행1 원하면 서로 영원히 기다린다. DB가 wait-for 그래프에서 cycle을 감지(`deadlock_timeout` 기본 1초 후)하고, victim을 골라 롤백시킨다. 앱은 재시도하면 된다.

### 상위/연관 개념
- **이벤트 루프 = PgBouncer의 원리**: PgBouncer는 프로세스를 fork하지 않고 이벤트 루프로 값싼 커넥션 수천 개를 받아서, 뒤의 비싼 Postgres 프로세스 소수에 다중화(깔때기)한다. 이건 [Flask + Gunicorn + gevent](/cs/flask-gunicorn-gevent-architecture/)에서 gevent가 워커 하나로 greenlet 수천 개를 굴리는 것과 똑같은 철학이다.
- **동기/비동기 스택**: [파이썬 웹 서버 async 스택](/cs/python-web-server-async-stack/) — WSGI/ASGI, 이벤트 루프의 기초.

### 비교 대상
- **HikariCP**(Java 커넥션 풀, Spring Boot 기본) ↔ **SQLAlchemy QueuePool**(Python, `SQLALCHEMY_POOL_SIZE`) ↔ **PgBouncer**(외부 프로세스 풀러). 이름만 다르지 "커넥션 재사용"이라는 개념은 다 똑같다.

## 느낀점

단순히 "풀은 커넥션 재사용하는 거"라고만 알고 있었는데, 그 밑에 이렇게 많은 게 깔려 있는 줄 몰랐다.

가장 인상 깊었던 건 **풀은 성능 장치일 뿐, 정합성은 완전히 다른 레이어**라는 점이다.
그동안 둘을 뭉뚱그려 생각했는데, 정합성은 DB의 트랜잭션·락·MVCC가 따로 책임진다는 걸 알고 나니 머릿속이 정리됐다.

그리고 "풀을 키우면 빨라지겠지", "DB CPU 늘리면 되겠지" 같은 직관이 대부분 틀렸다는 게 재밌었다.
풀은 프로세스마다 생겨서 결국 단일 DB의 `max_connections`로 수렴하고, 그래서 백엔드를 스케일아웃하면 오히려 DB가 위험해진다.
답은 "DB를 키우자"가 아니라 진단 → 튜닝 → decouple → scale up → scale out 순서라는 것.
이게 이번에 제일 크게 배운 점이다.

앞으로 실무에서 커넥션 관련 장애를 만나면, 이제는 어디부터 봐야 할지 감이 잡힌다.
