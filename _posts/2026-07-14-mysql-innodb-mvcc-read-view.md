## 한 줄 정의 (Feynman)
> **MVCC는 데이터를 덮어쓰는 대신 옛 버전을 살려둬서, 쓰기가 진행 중이어도 읽기가 기다리지 않고(락 없이) "자기 시점에 맞는 버전"을 골라 읽게 하는 장치예요.**

읽는 사람과 쓰는 사람이 동시에 오면 선택지는 딱 3개예요. ① 수정 중인 값을 그냥 보여준다(Dirty Read — 롤백되면 세상에 존재한 적 없는 값을 읽은 게 돼요), ② 쓰기가 끝날 때까지 읽기를 세운다(락 — 읽기 많은 서비스에선 재앙이에요), ③ **수정 전의 옛 버전을 보여준다.** MVCC는 ③이고, Multi-**Version**이라는 이름이 여기서 나와요. 대가는 두 가지 — 옛 버전을 보관할 공간(**undo log**)과, 어떤 버전을 보여줄지 판단하는 장부(**Read View**)가 필요해요.

---

## 1. 핵심 내용 / 구조

### 옛 버전은 어디에 — 행 뒤에 숨은 포인터 체인

InnoDB는 우리가 만든 컬럼 말고도 **모든 행에 숨은 컬럼을 몰래 붙여요** (MySQL 8.4 공식 문서로 확인):

| 숨은 컬럼 | 크기 | 역할 |
|---|---|---|
| `DB_TRX_ID` | 6바이트 | 이 행(버전)을 마지막으로 고친 트랜잭션의 ID — "이 버전을 만든 범인의 서명" |
| `DB_ROLL_PTR` | 7바이트 | 수정 전 내용이 적힌 undo log 레코드를 가리키는 포인터 |
| `DB_ROW_ID` | 6바이트 | PK가 없을 때만 클러스터드 인덱스용으로 쓰는 행 ID |

UPDATE가 일어나면 이전 상태가 undo log로 밀려나고, 포인터가 **연결 리스트처럼 과거로 이어져요**:

```text
[현재 행]   balance=500,  DB_TRX_ID=103 ──ROLL_PTR──▶
[undo 버전] balance=800,  DB_TRX_ID=100 ──ROLL_PTR──▶
[undo 버전] balance=1000, DB_TRX_ID=96  ──▶ ...
```

"옛 버전을 본다"는 건 마법이 아니라, **현재 행에서 출발해 이 체인을 과거 방향으로 따라 내려가는 것**이에요.

### 어떤 버전을 보나 — Read View라는 출석부

트랜잭션 ID는 시작 순서대로 커지는 번호표예요. 그런데 번호는 시작 순서만 알려주지 **커밋 여부는 안 알려줘요** (97번이 안 끝났는데 101번이 먼저 커밋할 수 있으니까요). 그래서 InnoDB 엔진 안에는 **`trx_sys`라는 전역 인메모리 관리소**가 하나 있고, 여기에 "지금 살아있는(시작했지만 미커밋) 트랜잭션 명단"이 실시간으로 유지돼요.

트랜잭션(내 번호 102라고 해요)이 **첫 평범한 SELECT를 하는 순간**, 이 관리소의 명단을 **복사**해서 내 것으로 만들어요. 이게 Read View(스냅샷)예요:

```text
        trx_sys (전역, 계속 변함)               내 Read View (복사본, 얼어붙음)
  ┌──────────────────────────┐    복사     ┌──────────────────────────┐
  │ 활성: {97, 100, 102}      │ ─────────▶ │ 활성 명단: {97, 100}      │
  │ 다음 번호: 103            │  (딱 1번)   │ 다음 번호: 103            │
  └──────────────────────────┘            └──────────────────────────┘
        ↑ 97이 커밋하면 여기선 빠짐              ↑ 여기는 영원히 안 바뀜
```

이후의 모든 행 읽기는 **행의 `DB_TRX_ID`를 이 복사본과 비교하는 산수**예요. trx_sys는 다시 안 봐요:

```text
보이는가(trx_id):
  1. trx_id == 102 (나 자신)       → 보임 (내가 고친 건 나한테 보임)
  2. trx_id < 97   (활성 최솟값 미만) → 보임 (스냅샷 전에 확실히 커밋됨)
  3. trx_id >= 103 (다음 번호 이상)  → 안 보임 (스냅샷 후에 시작한 미래)
  4. 97 ≤ trx_id < 103 구간이면:
       활성 명단에 있음(97,100) → 안 보임 (그때 미커밋이었음)
       활성 명단에 없음(예: 99) → 보임 (그때 이미 커밋하고 떠남)
```

"안 보임"이면 `DB_ROLL_PTR`을 타고 한 칸 과거로 내려가 같은 산수를 반복하고, **처음 "보임"이 나온 버전에서 멈춰요**. 위 체인 그림에서 내 스냅샷에 103·100이 안 보이면, 결과는 96번이 만들어둔 `balance=1000`이에요. 이게 MVCC 읽기 알고리즘의 전부예요.

이 장부는 디스크에 저장할 필요가 없어요 — 서버가 크래시하면 활성 트랜잭션도 다 죽으니까요. 그래서 역할 분담이 깔끔해요: **버전 데이터(undo log)는 디스크, 가시성 장부(trx_sys·Read View)는 메모리.**

### 읽기는 사실 두 종류

| | 스냅샷을 보나 | 락 |
|---|---|---|
| 평범한 `SELECT` (consistent read) | ✅ Read View 기준 과거를 봄 | 안 잡음 |
| `SELECT ... FOR UPDATE` / `FOR SHARE`, `UPDATE`, `DELETE` (locking read·쓰기) | ❌ **항상 최신 커밋 버전** | 잡음 |

쓰기 계열이 스냅샷을 무시하는 건 당연해요 — 과거 사진을 보고 데이터를 고치면 남이 바꾼 걸 모른 채 덮어쓰게 되니까요. 그래서 이런 기묘한 일이 생겨요:

```sql
-- REPEATABLE READ 트랜잭션 안에서
SELECT balance FROM accounts WHERE id=1;              -- 1000 (스냅샷)
-- 이 사이 다른 트랜잭션이 500으로 바꾸고 COMMIT
SELECT balance FROM accounts WHERE id=1;              -- 여전히 1000 (스냅샷)
SELECT balance FROM accounts WHERE id=1 FOR UPDATE;   -- 500!! (최신)
```

**같은 트랜잭션 안에서 같은 행이 다르게 보일 수 있어요.** 모르고 코드 짜면 실전에서 아프게 당하는 지점이에요.

### 격리 수준 = "스냅샷을 언제/어떻게 쓰나"의 스펙트럼

표준 4단계를 InnoDB의 평범한 SELECT 동작으로 다시 읽으면 한 축으로 꿰어져요:

| 격리 수준 | 평범한 SELECT의 동작 | 허용되는 이상현상 |
|---|---|---|
| READ UNCOMMITTED | 스냅샷 안 씀 — 현재 행 그대로 | Dirty Read부터 전부 |
| READ COMMITTED | 스냅샷을 **SELECT 문장마다** 새로 찍음 | Non-Repeatable Read, Phantom |
| REPEATABLE READ (MySQL 기본) | 스냅샷을 **트랜잭션당 한 번** (첫 SELECT 때) | (Phantom*) |
| SERIALIZABLE | 스냅샷 포기 — SELECT를 자동으로 `FOR SHARE`로 변환 | 없음 (대신 동시성 최소) |

```text
스냅샷 없음 ──── 문장마다 ──── 트랜잭션마다 ──── 락으로 회귀
    RU            RC             RR            SERIALIZABLE
```

양 끝이 재미있어요 — RU는 "MVCC를 안 쓰는" 수준이고 SERIALIZABLE은 "MVCC를 버리고 락으로 돌아가는" 수준이라, MVCC가 진짜 일하는 구간은 가운데 RC/RR이고 실무에서 쓰는 것도 사실상 이 둘뿐이에요.

이름과 메커니즘을 연결하면 외울 게 없어져요: **REPEATABLE READ** = 같은 SELECT를 반복해도 같은 결과(사진을 한 번만 찍으니까), **READ COMMITTED** = 커밋된 게 바로바로 보임(문장마다 새로 찍으니까).

(*) MySQL RR의 특이점: **스냅샷 읽기에선 팬텀이 안 보여요** — 스냅샷 이후 INSERT된 행은 DB_TRX_ID가 미래 번호라 출석부 산수가 자연히 걸러내니까요. 다만 잠금 읽기로 바꾸는 순간 최신 세계를 보므로 팬텀이 나타날 수 있고, 그걸 막는 게 **갭 락**이에요. "MySQL RR은 팬텀을 막는가?"의 답이 "스냅샷 읽기에선 막고, 잠금 읽기에선 갭 락이 있어야 막는다"인 이유예요.

## 2. 무엇을 배웠나

- MVCC의 세 축: **버전 체인(undo log) + 서명(DB_TRX_ID) + 출석부(Read View)**. 이 셋이면 읽기 경로 전체가 설명돼요.
- "스냅샷"의 실체는 신비한 게 아니라 **전역 trx_sys 명단의 순간 복사본**이에요. 원본은 계속 변하지만 복사본은 안 변하니까 REPEATABLE READ가 성립해요.
- 격리 수준은 별개의 4가지 모드가 아니라 **복사(스냅샷)를 하는 빈도의 스펙트럼**이에요.
- 장수 트랜잭션이 위험한 이유가 메커니즘에서 바로 나와요: 내가 오래된 스냅샷을 들고 버티면 InnoDB는 그 시절 undo 버전들을 못 지워요(purge 지연) → undo가 계속 쌓여요. 실무에서 만나는 **History List Length 폭증**이 이거예요. 공식 문서도 "consistent read만 하는 트랜잭션이라도 주기적으로 커밋하라"고 명시해요.
- 지난 [커넥션 풀 글](/cs/db-connection-pool-from-scratch/)에서 "풀은 성능 장치일 뿐 정합성과 무관하다"고 배웠는데, 그 정합성을 담당하는 실제 메커니즘이 오늘 판 MVCC예요.

## 3. 내가 오해하고 있던 것

> 이 세션에서 실제로 걸려 넘어진 순서대로예요. 제일 귀한 부분.

- **오해 ①: "MVCC = 커밋 안 된 더러운 값을 안 보려는 것"**
  - 정정: 절반만 맞아요. Read View는 미커밋 값뿐 아니라 **내 스냅샷 이후에 정상적으로 커밋된 값도 안 보여줘요** (RR 기준). 목표가 "Dirty Read 회피"가 아니라 **"특정 시점으로 시간을 고정한 일관된 읽기"**예요.
  - 왜 헷갈렸나: MVCC 소개가 대부분 Dirty Read 시나리오로 시작해서, 그게 전부라고 생각하기 쉬워요.

- **오해 ②: "가시성 판정은 매번 전역 진실원(trx_sys)과 비교하는 것"**
  - 정정: 전역은 **스냅샷 만들 때 딱 한 번** 방문하고, 이후 모든 비교는 **행의 번호 vs 내 복사본** 사이의 산수예요. 매번 전역을 보면 (1) 전역이 계속 변해서 "고정된 과거"가 안 되고 (2) 행마다 전역 자료구조에 락을 잡아야 해서 느려져요. 복사본이라서 락 없이, 변하지 않는 기준으로 판정할 수 있는 거예요.
  - 왜 헷갈렸나: "활성 트랜잭션 목록"이라는 말만 들으면 실시간 조회처럼 들려요. 핵심 단어는 **복사**예요.

- **오해 ③: "트랜잭션이 읽기를 시작한다 = 아무 SELECT나 한다"**
  - 정정: **평범한 SELECT만** 스냅샷 세계에 있어요. `FOR UPDATE`/`FOR SHARE`가 붙은 SELECT와 UPDATE/DELETE는 항상 최신 커밋 버전을 봐요(locking read). 그래서 같은 트랜잭션 안에서 같은 행이 다르게 보일 수 있어요.
  - 왜 헷갈렸나: "SELECT = 읽기"라고만 생각하면 수식어 하나(`FOR UPDATE`)가 읽기의 소속 세계를 통째로 바꾼다는 걸 놓쳐요. 읽기를 "스냅샷 읽기 / 잠금 읽기" 두 종류로 먼저 나눠야 이후 모든 게 맞아떨어져요.

- **오해 ④ (미리 잡은 것): "RR의 스냅샷은 START TRANSACTION 시점에 찍힌다"**
  - 정정: **첫 consistent read(첫 평범한 SELECT) 시점**이에요. 트랜잭션 열어놓고 10초 뒤 첫 SELECT를 하면 그 사이 커밋은 보여요. 시작 시점에 찍고 싶으면 `START TRANSACTION WITH CONSISTENT SNAPSHOT`을 명시해야 해요. (문서 원문: *"the snapshot established by the first such read in that transaction"*)

- **오해 ⑤ (세션 끝나고 나온 질문): "스냅샷 때문에 송금 같은 갱신은 오류가 날 수밖에 없다 — Write도 옛 값(100)을 볼 테니까"**
  - 정정: Write는 스냅샷을 안 봐요. 옆 트랜잭션이 200으로 바꾸고 커밋했으면 `UPDATE ... SET balance = balance - 50`은 **최신값 200 위에서** 실행돼 150이 돼요 (커밋 전이면 행 락에 걸려 기다려요). 그리고 UPDATE 직후의 SELECT는 "내가 만든 버전"이라 150이 보여요 — **내 쓰기가 스냅샷의 벽을 뚫는** 거예요.
  - 진짜 위험은 따로 있어요: **SELECT로 100을 앱으로 가져와 계산한 절대값을 UPDATE로 쓰는 패턴** (`SET balance = 50`). UPDATE는 최신 위에서 실행되지만 쓰는 값이 낡은 읽기로 계산된 거라 옆 트랜잭션의 변경이 증발해요 — 이게 **Lost Update**고, MVCC는 이걸 막아주지 않아요. MVCC의 약속은 "일관된 과거를 보여준다"까지지, "그 과거를 근거로 써도 된다"가 아니에요.
  - 그래서 송금 코드는 셋 중 하나로 짜요: ① 상대값 UPDATE(`balance = balance - 50`), ② 비관적 락(`SELECT ... FOR UPDATE`로 읽기부터 최신+락), ③ 낙관적 락(`UPDATE ... WHERE balance = 100`으로 조건 걸고 영향 행 0이면 재시도).
  - 왜 헷갈렸나: "트랜잭션 단위로 스냅샷을 기록한다"를 배우면 읽기·쓰기 모두 그 스냅샷 위에서 동작한다고 일반화하기 쉬워요. 오해 ③(읽기는 두 종류)이 여기서 실전 답을 갈라요.

## 4. 언제 쓰고, 언제 쓰지 않는가 (Trade-offs)

MVCC 자체는 InnoDB에서 끌 수 있는 게 아니라서, 실질적인 선택지는 "격리 수준 + 읽기 방식"이에요:

| 상황 | 선택 | 이유 |
|---|---|---|
| 일반적인 조회 (대부분의 읽기) | ✅ 평범한 SELECT (스냅샷) | 락 없음, 쓰기와 충돌 없음 |
| 읽은 값을 근거로 갱신 (잔액 차감 등) | ✅ `SELECT ... FOR UPDATE` | 스냅샷(과거)을 보고 쓰면 lost update — 최신을 보고 락으로 지켜야 해요 |
| 배치·리포트가 한 시점의 일관된 뷰 필요 | ✅ RR + 한 트랜잭션 | 스냅샷이 시점을 고정해줘요 |
| 트랜잭션을 몇 시간씩 열어두기 | ❌ | purge가 막혀 undo 폭증 (History List Length) — 읽기만 해도 위험해요 |
| 문장마다 최신이 보여야 하는 워크로드 | ⚠️ READ COMMITTED | 스냅샷을 문장마다 새로 — 대신 Non-Repeatable Read 감수 |

## 5. 직접 실험 / 검증

이번 세션은 실험 대신 **MySQL 8.4 공식 문서로 검증**했어요:

- [InnoDB Multi-Versioning](https://dev.mysql.com/doc/refman/8.4/en/innodb-multi-versioning.html) — 숨은 컬럼 3개의 이름·크기·역할, roll pointer와 undo 체인, "주기적으로 커밋하라"는 권고
- [Consistent Nonlocking Reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html) — RR은 첫 읽기 때 1회 / RC는 문장마다 스냅샷, locking read는 예외라는 것

**남겨둔 실험 목록** (다음에 Docker로 직접 확인할 것):

```sql
-- 터미널 2개로 재현할 것들
-- ① RR에서 옆 트랜잭션이 COMMIT해도 안 보이는 것 / RC로 바꾸면 보이는 것
-- ② 같은 트랜잭션에서 SELECT vs SELECT ... FOR UPDATE 결과가 갈리는 것
-- ③ 살아있는 트랜잭션 명단을 눈으로 보기:
SELECT trx_id, trx_state, trx_started FROM information_schema.INNODB_TRX;
-- ④ (불확실 → 확인 필요) 트랜잭션의 첫 문장이 SELECT가 아니라 UPDATE면
--    Read View가 그때 생기나, 이후 첫 SELECT 때 생기나?
```

소스 수준 디테일(trx_sys 내부 구현, Read View 필드명 `m_ids`/`m_up_limit_id`/`m_low_limit_id`)은 문서가 아닌 InnoDB 소스 이야기라 이 글에서는 구조만 가져왔어요.

## 6. 다른 개념과의 연결

- **상위 개념**: 트랜잭션 격리 수준, 동시성 제어 (낙관적 vs 비관적 — MVCC 읽기는 낙관 쪽, locking read는 비관 쪽)
- **하위/연관 개념**: undo log와 purge (History List Length), 갭 락·넥스트키 락 (RR에서 잠금 읽기의 팬텀 방지), redo log와의 역할 차이 (redo는 커밋 보존, undo는 롤백+MVCC)
- **같은 층의 이전 글**: [DB 커넥션 풀을 바닥부터 파헤치며 배운 것들](/cs/db-connection-pool-from-scratch/) — "풀은 성능 장치일 뿐 정합성과 무관하다"에서 멈췄던 그 정합성의 실제 메커니즘이 이 글이에요
- **비교 대상**: PostgreSQL의 MVCC — 같은 이름, 다른 구현이에요. PG는 undo log 없이 **테이블 안에 옛 버전 튜플을 그대로 남기고**(그래서 VACUUM이 필요) InnoDB는 undo로 밀어내요(그래서 purge가 필요). 이 비교는 따로 한 편 감이에요.
