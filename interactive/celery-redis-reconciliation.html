비동기 & 복원력 아키텍처

브로커를 믿지 않는 설계 — 비동기 인프라 Q&A와 회고

우리 백엔드는 Celery + Redis로 비동기 작업을 돌린다. 하지만 유실 방지의 축은 브로커의 내구성이 아니라, PostgreSQL을 진실원본으로 둔 주기적 재조정(reconciliation)에 있다. 나올 법한 질문들에 답하고, 왜 이렇게 설계했는지 강점·단점·트레이드오프까지 정리한다.

범위: Celery · Redis · beat · 재조정 근거: 실제 코드 확인 기준일: 2026-07-08
00

한눈에 — 구성요소와 역할

각 프로세스는 역할이 분리돼 있다. 무엇이 "전달"하고 무엇이 "실행"하며 무엇이 "진실"인지가 핵심.

Web

Gunicorn + gevent

HTTP 요청 처리. 무거운 일은 task로 넘김.

Transport

Redis (broker)

대기 중인 task 메시지를 나르는 큐. 휘발성.

Compute

Celery worker

큐에서 task를 꺼내 실제로 실행. 여러 대 가능.

Scheduler

Celery beat

정해진 주기에 task를 큐에 발행. 단일 프로세스.

Source of truth

PostgreSQL

상태·결과의 최종 진실원본. 재조정의 기준.

핵심 사상 한 줄: 우리 서버는 Redis를 "믿을 수 있는 저장소"로 취급하지 않는다. Redis는 빠른 전달 파이프일 뿐이고, 진짜 안 잃어야 할 것은 전부 PostgreSQL에 상태로 남긴 뒤, 여러 주기적 beat가 그 DB를 다시 읽어 어긋난 것을 맞춘다. 이건 K8s의 reconciliation loop, 그리고 outbox 패턴과 같은 계열의 설계다.

01

브로커 & 메시징

B1

Redis는 어디에 쓰나?

세 가지 역할이다. 혼동하면 안 된다.

  • Celery broker — 대기 중인 task 메시지 큐 (CELERY_BROKER_URL, rediss://면 TLS 자동).
  • 분산 락 / 캐시 — 디스패처 동시성 제어(락 키), 일부 상태 캐시.
  • 일시 상태의 TTL 저장소 — 예: 워크플로우 pause 키(TTL 만료를 타임아웃 신호로 활용).

주목할 점: task 결과 저장에는 안 쓴다(B4 참고).

B2

Redis가 죽으면 어떻게 되나? 휘발되는데?

persistence(AOF)나 replica가 없으면, 큐에서 대기 중이던 메시지는 사라진다. 다만 피해는 생각보다 좁고, 세 층으로 방어된다.

  • 무사 이미 실행 중인 task — 워커 메모리에서 돌고 있어 Redis와 무관하게 완료. 결과는 DB에 씀.
  • 실패 신규 발행(.delay()) — Redis 연결이 안 되면 발행 자체가 예외. 아래 재조정이 흡수.
  • 복구 대기 메시지 유실 — "해야 할 일"이 DB에 상태로 남아 있으므로, 주기 beat가 DB를 재스캔해 재발행(R1·R2).
핵심 Redis 휘발이 곧 작업 유실이 아니다. 진실원본이 DB라서, Redis는 "다시 채울 수 있는 캐시"에 가깝다.
B3

task가 유실될 수 있나? (acks_late)

순수 Celery 관점에선 유실될 수 있다. 우리 설정은 task_acks_late를 지정하지 않아 기본값 False다.

  • acks_late=False → 워커가 task를 받는 순간 ACK. 그래서 실행 도중 워커가 죽으면(OOM/SIGKILL) 그 메시지는 이미 큐에서 지워져 자동 재시도되지 않는다.
  • worker_prefetch_multiplier=1이라 선점량이 최소여서 유실 범위는 "진행 중이던 그 1개"로 작다.
그래서 왜 괜찮은가 Celery 레벨 재시도가 없어도 DB 재조정 beat가 "멈춘 문서/실행"을 잡아 재큐한다(R2). 유실 방지의 축이 브로커가 아니라 DB에 있다는 증거.
B4

task 결과는 어디에 저장되나?

Redis가 아니라 PostgreSQL. CELERY_BACKEND 기본값이 database라 결과 backend는 db+postgresql://…로 잡힌다. 게다가 task_ignore_result=True라 결과를 사실상 담지도 않는다.

의미: "Redis 죽으면 결과가 날아간다"는 문제는 애초에 존재하지 않는다. Redis는 오직 대기 메시지 파이프.

02

워커

W1

워커가 죽으면?

워커는 여러 대 띄울 수 있어 한 대가 죽어도 다른 워커가 큐를 계속 소비한다. 문제는 죽은 워커가 실행 중이던 그 task인데(B3), 이건 재조정으로 복구된다:

# 임베딩 예: worker 급사 → 15분 뒤 stale 회수가 되살림 상태 = 처리중 AND 처리시작시각 < now - cutoff # 멈춤 감지 → 발행시각 초기화, 상태=대기 # 재큐

즉 워커 크래시 복구는 Celery가 아니라 DB 상태 + beat가 담당한다.

W2

큐를 왜 여러 개로 나눴나?

작업 특성별 격리 때문. 무거운 인덱싱이 가벼운 메일 발송을 막지 않도록, 그리고 장시간 작업이 짧은 작업의 지연을 유발하지 않도록 큐를 분리하고 워커를 큐별로 배치한다.

큐용도
dataset문서 인덱싱·데이터 처리
memory메모리 추출·리임베딩
longrun장시간 실행 Job
cleanup정리·회수 (재조정 안전망 포함)
mail · slack알림 발송
monitoring모니터링·통제 작업

라우팅은 task_routes로 선언(예: memory task → memory 큐). 새 큐는 워커 실행 옵션(-Q)에도 등록해야 실제로 소비된다.

W3

타임아웃 정책은?

글로벌 기본 soft_time_limit=600(10분), task_time_limit=660(+1분 버퍼). soft는 graceful 종료 기회를 주고, hard는 강제 kill.

10분 넘게 걸리는 task는 개별로 상향한다(패턴: time_limit = soft + 60). 예: 인덱싱 30분(1800/1860), 장시간 분석 2시간(7200/7260). soft 초과 시 SoftTimeLimitExceeded를 잡아 정리 작업을 수행.

03

beat & 스케줄링

S1

beat가 뭔가?

스케줄러(크론) 프로세스. 정해진 시각/주기마다 task를 큐에 발행만 한다 — 실행은 워커가 한다. 리눅스 cron을 Celery 안으로 가져온 것.

프로세스역할비유
worker큐에서 꺼내 실행요리사
beat때맞춰 발행주문 타이머
broker그 사이 큐주문 선반

우리 재조정 루프(안전망 60초, stale 회수 15분, 앱 스케줄러 매분 등)는 전부 beat가 굴린다. 그래서 이름도 beat(박동).

S2

beat가 죽으면? — 이 아키텍처의 급소

가장 약한 고리다. 정직하게:

  • 재조정 루프를 전부 beat가 굴리는데, beat 자신은 이중화가 없다. redbeat·리더선출을 안 쓴다(기본 PersistentScheduler).
  • beat를 2개 띄우면 모든 주기 task가 2번씩 발화(중복) → 구조적으로 단일 인스턴스 = SPOF
  • 워커·Redis 장애는 beat가 자가치유하지만, beat 장애를 자가치유하는 상위 안전망은 코드에 없다.
그럼 무엇이 beat를 살리나 애플리케이션이 아니라 오케스트레이터(Docker restart policy / K8s liveness probe)가 죽은 beat를 재시작한다. 내결함성이 "이중화"가 아니라 "단일 프로세스 빨리 되살리기"에 위임돼 있다.

Java 대응: @Scheduled도 같은 문제라 ShedLock(분산락)으로 하나만 활성화한다. 즉 파이썬 한계가 아니라 "단일 리더 스케줄러" 개념 자체의 성질.

S3

다운 중 놓친 일정은 backfill 되나?

  • crontab 기반(예: 매일 02:00 정리) — 다운타임 중 놓친 실행은 backfill 안 됨. 다음 매칭 시각에 정상 발화.
  • interval 기반(timedelta) — 재시작 시점부터 다시 카운트.

다만 놓친 만큼의 "해야 할 일"은 DB에 남아 있어, 복구 직후 첫 스캔에서 한꺼번에 따라잡는다. 그 폭주를 막으려고 beat에 options={"expires": N}을 걸어 다음 주기와 안 겹치게 만료시킨다.

04

재조정(reconciliation)

R1

beat는 "어디까지 실행됐는지" 어떻게 아나?

beat가 아는 게 아니다. worker가 진행하면서 자기 발자국을 DB row에 계속 써넣는다. beat는 그걸 읽고 상태를 역추론할 뿐. 임베딩 예의 상태 컬럼:

컬럼언제 채워지나의미
큐 등록 시각디스패처 경유 등록"재조정 대상" 표식
발행 시각큐에 발행한 시각발행됨, 실행은 아직
처리시작 시각워커가 처리 시작실행 시작함
진행 상태단계 진행마다대기→…→완료/오류
세대 번호회수 시 +1fencing token
# beat는 컬럼 조합 + 경과시간으로 상황을 분류 대기 + 큐등록✓ + 발행시각 없음 → 즉시 발행 대기 + 발행✓ 인데 2h 경과 → 재큐 # 브로커 소실 처리중 + 처리시작시각 임계 초과 → 재큐 # 워커 급사
중요한 한계 beat가 아는 진행은 거친 체크포인트뿐이다. "500청크 중 300개 했다"는 모른다. 그래서 재처리는 문서 단위 통째로 다시 하고, 그 안전장치가 멱등성이다(R3).
R2

재조정 예시가 임베딩 말고 또 있나?

임베딩은 가장 최근 사례일 뿐, 같은 골격이 여러 도메인에 이미 있다. 성격별로:

A. 장애 복구형

사례상태원본주기특징
임베딩 회수status·*_at15분기준 사례
워크플로우 stale실행 상태 + 시각5분finally 유실분 2차 방어
장시간 Job stale하트비트 시각5분하트비트 방식

B. 시간 만료형

사례상태원본주기특징
Interrupt 타임아웃PAUSED + Redis TTL5분Redis 휘발을 신호로
API 키풀 복구리셋 예정 시각1분시각 지나면 복귀
앱 차단 자동해제차단 만료 시각1분멱등 명시

두 가지가 임베딩엔 없던 새 변형이다:

  • 하트비트(장시간 Job) — 단일 시작시각으론 "정상적으로 오래 걸림"과 "죽어서 멈춤"을 구분 못 한다. 실행 중 계속 하트비트 시각을 갱신하면 그 둘을 정확히 구분.
  • Redis TTL + DB 이중상태(Interrupt) — pause를 Redis 키(TTL)+DB PAUSED로 둔다. Redis 키가 만료·소실되면 → "타임아웃"으로 판정해 DB를 FAILED로 마감. Redis의 휘발성을 오히려 신호로 쓴다.

가장 근본은 앱 스케줄러(매분): "DB(스케줄 설정)를 진실원본으로, beat가 주기적으로 읽어 행동"하는 패턴의 원형이다.

R3

재처리가 중복 실행일 텐데 왜 안전한가?

이 모델은 at-least-once다(최소 한 번, 중복 가능). 그래서 두 안전장치가 필수다:

  • 멱등성(idempotency) — 같은 작업을 다시 해도 결과가 같아야 함. 예: 같은 청크를 재삽입해도 중복 row가 안 생기게.
  • fencing token(세대 번호) — 죽은 줄 알고 재발행했는데 원래 워커가 되살아나 둘이 동시에 돌면? 회수 시 세대를 +1 해서 낡은 세대의 write를 무시, 정합성을 보존.

이 둘이 없으면 재조정은 곧 데이터 오염이 된다. 그래서 "재조정 설계 = 멱등 설계"가 세트다.

05

Redis 고가용성

H1

마스터-슬레이브 승격이나 TTL 같은 게 있나?

있다 — Redis Sentinel(옵션). CELERY_USE_SENTINEL=true면 broker transport에 master_name과 sentinel 설정이 붙는다.

  • Sentinel이 마스터를 감시하다 죽으면 슬레이브를 새 마스터로 자동 승격(failover). 클라이언트는 Sentinel에 물어 새 마스터로 재접속. Kafka 파티션 리더 재선출과 같은 개념.
  • 주의: 기본값은 off. 프로덕션 HA가 필요하면 Sentinel(또는 managed Redis failover)을 반드시 켜야 한다 — 안 켜면 단일 Redis가 SPOF.

TTL 관점: 브로커 대기 메시지엔 TTL이 없다(워커가 가져갈 때까지 유지). 대신 beat 스케줄에 expires를 걸어 복구 시점 폭주를 막고, 애플리케이션 상태(pause 등)엔 Redis TTL을 걸어 타임아웃 신호로 쓴다(R2). visibility_timeout은 명시 설정이 없어 Redis 트랜스포트 기본값(1시간)이며, acks_late를 안 쓰는 현 구성에선 실질 영향이 작다.

06

왜 이렇게 설계했나 — 회고

자바의 Kafka+outbox 결제 방어와 비교하며. 결론: 잘못된 설계가 아니라 워크로드에 맞춘 의도된 트레이드오프.

설계 의도 "진짜 안 잃어야 할 상태는 이미 PostgreSQL에 있다. 그러면 브로커 내구성에 돈·복잡도를 쓸 게 아니라, DB를 주기적으로 재조정하면 된다." — Kafka+outbox의 앞부분(브로커 내구성)을 생략하고, 진짜 안전망인 뒷부분(DB 재조정)만 남긴 선택.
선택지장점단점우리 판단
A. Kafka 도입
(자바식)		 내구성·순서보장·오프셋 되감기 운영·학습 비용 큼 과설계 백그라운드 작업엔 이득<비용
B. Redis durability
(AOF·Sentinel)		 대기 메시지 휘발 감소 여전히 브로커를 "믿음", 워커 크래시 유실은 못 막음 부분 채택 Sentinel은 옵션 제공
C. DB 재조정
(채택)		 브로커를 안 믿음 → 휘발·크래시와 무관, 가벼움 지연(폴링)·멱등 강제·beat SPOF 채택 가장 튼튼한 층만 취함

강점

  • 브로커 비의존 — Redis 휘발·워커 크래시가 최종 정합성을 깨지 못한다.
  • 검증된 사상 — K8s reconciliation, outbox의 backstop과 동일 계열.
  • 가벼움 — Kafka 없이 이미 있는 DB만으로 복원력 확보.
  • 도메인 확장 용이 — 상태 컬럼 + beat만 추가하면 새 재조정이 생긴다(이미 7+ 사례).

단점 / 트레이드오프

  • 복구 지연 — 즉시가 아니라 다음 주기(수 분). 초 단위 정확성엔 부적합.
  • at-least-once — 중복 실행 가능 → 모든 task 멱등 강제.
  • beat SPOF — 재조정의 심장이 단일. 코드가 아닌 운영(restart/liveness)이 책임.
  • exactly-once 불가 — 강한 트랜잭션 보장이 필요한 도메인엔 부족.
파이썬 한계인가? 아니다. Java로 짜도 같은 구조가 나온다: @Scheduled/Quartz = beat, ShedLock = redbeat(분산락), Spring Batch = 재조정 잡. beat SPOF는 언어가 아니라 "단일 리더 스케줄러" 개념의 성질이다.
재설계 시그널 강한 순서보장이나 exactly-once가 요구되는 도메인(예: 결제)이 생기면 — 그때는 Kafka + transactional outbox 정통 구현을 도입할 값어치가 있다. 지금 워크로드(임베딩·인덱싱·정리·토큰갱신)엔 현 구조가 맞다. 유일하게 규율이 필요한 곳은 "배포에서 beat가 restart/liveness로 확실히 살아있게 걸려 있는가" 하나.
